# Übersetzung (Deutsch / Englisch)

diggy gibt es auf Deutsch und Englisch (#86). Deutsch ist die Quelle, Englisch
wird nachgeladen. Diese Seite beschreibt den Aufbau und — vor allem — wie ein
neuer Text dazukommt.

## Kurzfassung

Neuer sichtbarer Text:

1. Im Code `t('Deutscher Text')` statt `'Deutscher Text'` bzw. `<p>Deutscher Text</p>`.
2. Den Text in `src/i18n/de.ts` in die Union `DeText` eintragen (im passenden Abschnitt).
3. In `src/i18n/en.ts` unter demselben Schlüssel übersetzen.

Der Compiler führt durch die Schritte 2 und 3: ohne Eintrag in `de.ts` scheitert
`t()`, ohne englische Fassung scheitert `en.ts`. `npm run i18n` findet Texte,
die am Modul vorbeilaufen (Schritt 1).

## Aufbau

| Datei | Inhalt |
|---|---|
| `src/i18n/index.ts` | Laufzeit: Sprache, `t()`, `tRich()`, Intl-Formate, `useI18n()`, Übersetzung von Findings und Fehlern |
| `src/i18n/de.ts` | Alle deutschen Texte als Typ (`DeText`) und die Pluralformen (`DE_PLURALS`) |
| `src/i18n/en.ts` | Englisches Wörterbuch für die Oberfläche — eigener Chunk |
| `src/i18n/en.server.ts` | Englisch für Findings und Fehlermeldungen des Servers (im selben Chunk) |
| `shared/textKeys.ts` | Kennungen der Findings und Fehlercodes — der Vertrag zwischen Server und Client |
| `scripts/check-i18n.mjs` | Prüfskript (`npm run i18n`, läuft in `verify`) |

### Der deutsche Text ist der Schlüssel

`t('Menü öffnen')`, nicht `t('header.openMenu')`. Der Grund ist das
Bundle-Budget: index.js lag bei 46 von 48 kB gzip. Mit Schlüsseln stünde jeder
Text zweimal als Kennung im kritischen Pfad (Wörterbuch und Aufrufstelle) —
gemessen gut 5 kB für 400 Texte. So braucht das deutsche Bundle kein
Wörterbuch, es bleibt der Aufruf `t(…)` selbst.

`de.ts` ist trotzdem die Quelle: die Union `DeText` legt fest, welche
Schlüssel es gibt, und kostet als reiner Typ nichts. Ausgeliefert wird nur
`DE_PLURALS`, weil die Einzahl an keiner Aufrufstelle steht.

### Sprache

- **Voreinstellung**: die erste unterstützte Sprache aus `navigator.languages`
  (`de-AT` → Deutsch, `fr, de` → Deutsch, `fr` → Englisch).
- **Wahl im Menü**: unter „Theme“, gespeichert in `localStorage`
  (`diggy-language`). Die erkannte Sprache wird nicht gespeichert — sonst
  überstimmte sie später eine geänderte Browser-Einstellung.
- `<html lang>` und `document.title` folgen der Sprache. `index.html` und die
  Link-Vorschau bleiben deutsch.
- **Laden**: `en.ts` ist ein eigener Chunk und wird nur bei Englisch geholt.
  Englische Besucher rendern erst, wenn er da ist — statt einer deutschen
  Seite, die dann umspringt; nach 1,5 s wird auf jeden Fall gerendert
  (`main.tsx`). Damit das kaum Zeit kostet, stößt ein Inline-Script in
  `index.html` den Chunk parallel zu `index.js` an (`modulepreload`, Pfad
  setzt `vite.config.ts` ein). Es wiederholt die Regel von
  `detectLanguage()`; `i18n.test.ts` hält beide gleich. Gemessen auf
  „Fast 3G“: erste Ansicht 60 ms nach der deutschen statt 650 ms.
  Ein Wechsel im Menü schaltet um, sobald das Wörterbuch da ist — bis dahin
  bleibt alles deutsch, kein Zwischenzustand.
- **Tests** laufen auf Deutsch (`src/test/setup.ts`); jsdom meldet `en-US`.

## Texte schreiben

### Platzhalter

```tsx
t('Geprüft am {date}', { date: formatDate(report.timestamp) })
```

Platzhalter heißen in beiden Sprachen gleich (geprüft in `i18n.test.ts`).
Zahlen werden im Format der Sprache eingesetzt (1.234 / 1,234). Fehlt ein Wert,
bleibt `{name}` sichtbar stehen.

### Mehrzahl

Die Zahl heißt immer `count`. Braucht das Deutsche Einzahl und Mehrzahl, steht
der Text in `DE_PLURALS` (Mehrzahl als Schlüssel, Einzahl als Wert) statt in
`DeText`:

```ts
// de.ts
'noch {count} Tage': 'noch {count} Tag',
// en.ts
'noch {count} Tage': { one: '{count} day left', other: '{count} days left' },
```

Englisch darf Einzahl und Mehrzahl auch dort unterscheiden, wo das Deutsche
keine braucht (`'Noch mindestens {count} Zeichen'` → „1 more character“ /
„3 more characters“): der Text bleibt dann in `DeText`, `en.ts` gibt ein
`{ one, other }`.

### Elemente im Satz

Links oder Hervorhebungen mitten im Satz über `tRich()` — sonst zerfällt der
Satz in Stücke, deren Reihenfolge im Englischen nicht mehr stimmt:

```tsx
tRich('Details unter {link}.', { link: <button …>{t('Datenschutz')}</button> })
```

### Datum und Zahl

`formatDate()` und `formatNumber()` aus `useI18n()` statt `toLocaleString('de-DE')`.

### Wann kein `t()`

- **Fachbegriffe und Namen**, die in beiden Sprachen gleich heißen: Records,
  Health Score, SPF, DMARC, WHOIS, Propagation, PageSpeed. Sie laufen nicht
  durch das Modul.
- **Bewusst deutsch**: Rechtstexte. Ein Element mit `lang="de"` und sein
  Inhalt sind ausgenommen (Impressum), ebenso eine Datei mit dem Kommentar
  `i18n-ignore-file` (Datenschutztext). Auf Englisch steht darüber
  `<GermanOnlyNotice />`.
- **Log-Ausgaben** (`console.*`).

### Texte in Tabellen

Konstanten auf Modulebene halten den Schlüssel, übersetzt wird beim Rendern:

```tsx
const STATUS: Record<Status, { label: DeKey }> = { available: { label: 'Verfügbar' } };
// …
<span>{t(STATUS[status].label)}</span>
```

Der Typ `DeKey` sorgt dafür, dass nur Schlüssel aus `de.ts` dort stehen.

### Gleicher deutscher Text, verschiedenes Englisch

Ein deutscher Text ist genau ein Schlüssel. Braucht das Englische an zwei
Stellen zwei Fassungen, muss sich auch der deutsche Text unterscheiden
(Groß-/Kleinschreibung, Mehrzahl, ein Wort mehr). Beispiel: das Badge
„Warnung“ (`Warning`) und die Legende „3 Warnungen“ (`3 warnings`).

### Englischer Stil

Wie das Deutsche: freundlich, knapp, „you“ statt Passiv („DNS made
friendly“). Amerikanische Schreibweise. Englische Texte sind oft länger —
in schmalen Spalten und Buttons auf 390 px prüfen.

## Findings und Server-Meldungen

Der Server schreibt weiter auf Deutsch. Alte Clients, die API und der
JSON-Export bleiben damit unverändert. **Additiv** trägt jedes Finding eine
Text-Kennung und die Werte aus dem Satz:

```json
{ "id": "ssl-expiring-soon", "title": "Zertifikat läuft in 5 Tagen ab", "params": { "count": 5 } }
```

- Die Kennung ist die `id`, außer ein `key` steht dabei — nötig, wo eine `id`
  mehrere Sätze kennt (Apex/Host, mit/ohne MX) oder dynamisch ist
  (`spf-issue-…`).
- Auf Deutsch zeigt der Client die Texte des Servers. Auf Englisch setzt er
  den Satz aus `en.server.ts` und den Werten zusammen.
- Unbekannte Kennung oder fehlender Wert (z. B. ein Report von vor #86): es
  bleibt beim deutschen Text — nie ein halber Satz.

### Neues Finding

1. In `server/services/reportBuilder.ts` wie bisher anlegen, mit deutschem
   Titel und Beschreibung. Werte aus dem Satz zusätzlich als `params`, die
   Zahl für die Mehrzahl als `count`.
2. Der Compiler meldet die unbekannte `id` (Typ `KeyedFinding`): die
   Kennung in `shared/textKeys.ts` unter `FindingKey` eintragen.
3. Jetzt meldet `en.server.ts` den fehlenden Eintrag: Titel, Beschreibung und
   — falls das Finding einen Fix mit Erklärung hat — `fix` übersetzen.
4. Den Vertragstest `src/i18n/findings.test.tsx` um eine Eingabe ergänzen,
   die das Finding erzeugt. Er verlangt beides: jedes erzeugte Finding hat
   eine vollständige Übersetzung, und jeder Eintrag wird erzeugt.

### Neue Fehlermeldung

Fehler kommen als `{ error, message }`. Der Client übersetzt nach `error`
(`ApiErrorCode` in `shared/textKeys.ts`, Text in `apiErrors` in
`en.server.ts`). Setzt der Server Werte in die Meldung ein, gibt er sie als
`params` mit (Beispiel: `invalid_domain` mit `{ input }`). Ein unbekannter
Code zeigt die deutsche Meldung des Servers.

Die Codes stehen im Server als String-Literal, der Compiler sieht sie dort
nicht. `findings.test.tsx` liest sie deshalb aus dem Quelltext (`error: '…'`,
`code: '…'`, `sectionError(res, '…')`) und verlangt für jeden einen Eintrag in
`apiErrors` — und umgekehrt. Ein neuer Code: in `ApiErrorCode` eintragen,
dann meldet der Compiler den fehlenden englischen Text.

Kommt keine JSON-Antwort (Fehlerseite eines Proxys), wirft `lib/api.ts` den
eigenen, schon übersetzten Ersatztext ohne Code.

## Prüfskript

`npm run i18n` (Teil von `npm run verify`) meldet:

- deutschen JSX-Text und deutsche Attribute (`aria-label`, `title`,
  `placeholder` …),
- deutsche Strings außerhalb von `t()`/`tRich()`, die kein Schlüssel aus
  `de.ts` sind,
- Schlüssel in `de.ts`, die nirgends mehr vorkommen.

„Deutsch“ erkennt es an Umlauten, typischen Wörtern („und“, „nicht“,
„keine“ …) und Endungen (-ung, -keit, -lich …). Das ist bewusst vorsichtig:
es meldet keine englischen Texte, Klassen oder Kennungen (geprüft gegen alle
409 englischen Texte und den ganzen Quelltext), übersieht dafür einzelne
neutrale Wörter wie „Kalender“. Gegen den Stand vor der Übersetzung fand es
271 Stellen; das Englische fängt der Rest — ein Blick auf die Seite auf
Englisch gehört zu jeder neuen Oberfläche.

## Nachziehen: Texte aus parallelen PRs

Dieser PR kommt als letzter. Was die anderen PRs an deutschen Texten mitbringen,
wird nach dem Rebase mechanisch nachgezogen:

1. `git rebase origin/main`, Konflikte in den Komponenten lösen: deren neue
   Texte bleiben zunächst als deutscher String stehen.
2. `npm run i18n` listet jede Stelle mit Datei und Zeile.
3. Je Stelle: `t('…')` drumherum (oder `tRich`, wenn ein Element im Satz
   steht), den Text in `de.ts` eintragen, in `en.ts` übersetzen. Datum und
   Zahlen auf `formatDate`/`formatNumber` umstellen.
4. `npm run typecheck` — meldet vergessene Einträge in `de.ts`/`en.ts` und neue
   Finding-Kennungen ohne Eintrag (siehe „Neues Finding“).
5. `npm test` — der Vertragstest verlangt für neue Findings eine Eingabe in
   `everyFinding()` und für neue Fehlercodes des Servers einen Text (siehe
   „Neue Fehlermeldung“); der Platzhaltertest prüft die neuen Übersetzungen.
6. Einzelne neutrale Wörter, die das Skript nicht erkennt: den Diff der
   anderen PRs nach JSX-Text und `label=`/`title=` durchsehen und die Seite
   auf Englisch öffnen.
